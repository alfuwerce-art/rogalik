**На Windows:** `C:\Users\bow\Desktop\Rogalik\assets\references\gpt_asset_library`
**Владелец художественного содержимого:** ChatGPT (D24). **Интеграция:** DeepSeek Harness. **Основная ветка работ:** фактическая рабочая ветка этапа (сейчас `stage3-hero`), не `main`.

**D31 (01.11.2026) уточняет D30:** эта папка — каталог *всех новых* художественных файлов GPT, готовых PNG и кадров. Старые референсы, архивы и технические прокси **не переезжают автоматически**. Весь новый художественный контент имеет один постоянный ID и один `asset.json`; все существующие экземпляры фиксируются по реальным файлам и SHA-256.

## 1. Точная архитектура: две зоны, один источник истины

1. **Библиотека GPT** (`assets/references/gpt_asset_library/`) — оригиналы `sources/`, визуальные эталоны `master/`, очищенные **игровые экспорты** `frames/`, `sprites/`, `tiles/`, `exports/`, производные `atlases/` и карточка `asset.json`. Это **источник истины по художественным файлам**; файлы в других каталогах не заменяют его историю/метаданные.
2. **Godot-ресурсы** — для *новых GPT-экспортов*, принятых для интеграции, зеркальная **производная копия** в `game/prototype/art/gpt/<category>/<ID>_<slug>/...`, с путями Godot `res://art/gpt/...`. В игровые каталоги не копируются `master/`, `sources/`, неутверждённые референсы и preview. Не менять существующие `res://art/sprites/...` без проверки зависимостей.
3. DeepSeek не рисует и не перегенерирует художественные кадры. Он подтверждает наличие, SHA, готовность, делает безопасную техобработку и интеграцию. Если художественная ошибка — возвращает на генерацию в ChatGPT.

```text
│       ├── sources/              # оригинальные GPT-изображения, без изменения пикселей
│       ├── frames/

```

Дерево — **контракт размещения**, а не утверждение, что эти файлы уже есть. На диске можно создать все категории. **Не добавлять вымышленные кадры и пустые анимации в индекс.** Пустые папки Git не хранит; при необходимости создавайте по мере фактической передачи ассетов, без десятков бессмысленных `.gitkeep`.

**Типы:**
- `characters` / `enemies` / `bosses`: художественные кадры идут в `frames/<clip>/<direction>/`. Для H01 8 направлений по D29; вражеские направления уточнять в их собственном контракте, не копировать автоматически восемь.
- `weapons`: статический кадр в `sprites/`, движущиеся кадры — `frames/<action>/<direction>/`; `grip_anchor` в метаданных. Не вшивать оружие в базовое тело H01.
- `props`: статическая бочка/сундук — `sprites/`; анимационный проп — `frames/<clip>/` (директория направления только при необходимости); `ground_pivot`, `world_footprint_tiles` фиксировать.
- `environment`: строения/деревья/детали локации — `sprites/`, слои перекрытия и иные художественные части — `layers/` при необходимости; коллизии и сортировка — в Godot.
- `tilesets`: отдельные тайлы `tiles/`, исходная нарезка/атлас `atlases/`; профиль HD4X **96×96 source px на одну клетку** при 24 world units, проверка стыков 2×2. Не путать одиночную текстуру и тайлсет.
- `textures`: готовая однофайловая/повторяемая поверхность в `exports/`; `tileable` отмечать только после проверки повторения.
- `vfx`: `frames/<effect>/`, либо `frames/<effect>/<direction>/` при направленном эффекте; свечения могут быть полупрозрачными.
- `ui`: `exports/` для отдельных иконок/интерфейсных элементов с экранным DPI, не применять к ним рост H01 в 192px.

## 3. Жёсткие имена и уникальные ID

- **ID берётся из** `docs/ART_ASSET_ANIMATION_REGISTRY.md` и иных утверждённых реестров. Если нужен новый — перед выдачей проверить уникальность **регистронезависимо** по всем категориям; не выдумывать задним числом «PR001», если такой ID не принят. Один ID → одна папка → один `asset.json`. Категорию не определять по имени файла на глаз.
- `<ID>_<slug>` — идентификатор + понятное ASCII `snake_case` имя. Существующий каталог `H01_hero` оставить, не переименовывать. Нельзя смешивать русские имена, пробелы, скобки `(1)`, `final2`, `copy`, случайные префиксы генератора в **канонических игровых** именах.
- Для кадров персонажа: `<ID>_<clip>_<direction>_<NNN>.png`, например `H01_idle_down_right_000.png`. `NNN` с нуля, три цифры, без пропусков внутри завершённого клипа; `frame_index` и `order` в манифесте.
- Для статичных изображений: `<ID>_static_000.png`. Для тайла: `<ID>_<surface>_<variant:03d>.png`. Для VFX: `<ID>_<effect>_<NNN>.png`, при направлениях указывать `direction` в пути и манифесте.
- Канонические файлы PNG не перезаписывать поверх опубликованной принятой версии без явного решения владельца. GPT-оригиналы хранить *неизменно* в `sources/`, при коллизии имени добавлять версию `_v02` и записывать `original_filename` в `asset.json`. Кандидаты, не прошедшие технический экспорт, остаются в `sources/`, а не в `frames/` как GAME_EXPORT.

## 4. Внутренние параметры — записывать, а не угадывать

**Корневой `asset_index.json`** хранит уникальные `asset_id`, `category`, `slug`, относительный `manifest_path`, `presence`, `readiness`. Относительные пути считаются от `assets/references/gpt_asset_library/`, используют `/` даже на Windows и не выходят за пределы корня через `../`.

**Каждый `asset.json`**:
- `asset_id`, `category`, `display_name`, `source_author=ChatGPT`, `profile_id`;
- `master`: неизменяемый SHA-256, фактический внешний/внутренний путь, отдельный статус `VISUAL_APPROVED`;
- `files[]`: только **фактически существующие** файлы. Для каждой записи указывать `path` (от корня библиотеки), `role` (`source`, `game_export`, `atlas` и т. п.), `sha256`, `file_type`, `canvas_px`, `pivot_px` и при кадрах `animation`, `direction`, `frame_index`; необязательные: `visible_bbox_px`, `source_path`, `world_footprint_tiles`, `fps` (только утверждённое значение), `grip_anchor_px`, `alpha_policy`, `godot_resource_path`;
- `animations` — группы реальных файлов по клипу и направлению, порядок/FPS по факту; 8 папок направлений не означает 8 готовых направлений;
- `status`: **раздельно** `presence`, `technical_export`, `godot`, `art_approval`, `github`; `godot_resource_path` фактический или `null`.

**Базовый статус H01 после D30:** `master.visual_status=VISUAL_APPROVED_D25`, но бинарник мастера в GitHub не подтверждён; `files=[]`, `status.presence=NOT_IMPORTED`, `godot=GODOT_NOT_TESTED`. Если владелец положит `H01_idle_down_right_000.png` локально в правильную папку, DeepSeek сначала измеряет его и добавляет **проверенную запись**. Не объявлять `ART_APPROVED` по факту копирования.

## 5. Разница между источниками, кандидатами и Godot

`master/` и `sources/` — визуальные материалы, обычно не импортируемые в Godot как игровые ресурсы. `frames/`, `sprites/`, `tiles/`, `exports/` — нормализованные PNG `GAME_EXPORT`. `atlases/` — производные из проверенных отдельных PNG, не замена оригиналов.

В Godot зеркальная структура новых экспортов:
```text
game/prototype/art/gpt/
├── characters/H01_hero/frames/idle/down_right/H01_idle_down_right_000.png
├── enemies/<ID>_<slug>/...
├── bosses/<ID>_<slug>/...
├── weapons/<ID>_<slug>/...
├── props/<ID>_<slug>/...
├── environment/<ID>_<slug>/...
├── tilesets/<ID>_<slug>/...
├── textures/<ID>_<slug>/...
├── vfx/<ID>_<slug>/...
└── ui/<ID>_<slug>/...
```
**Не** перемещать `CharacterBody2D`, сцены, коллизии или `game/prototype/art/sprites/` наугад. Путь `res://art/gpt/...` подтверждается только реальным Godot-импортом. Подготовленный PNG может физически существовать и быть `TECHNICAL_EXPORT_PASS`, но ещё `GODOT_NOT_TESTED`; это не ошибка именования.

## 6. Правила безопасного наведения порядка (задача DeepSeek)

1. Проверить `git status`, рабочую ветку и актуальность `origin`. **Не** выполнять `git clean -fd`, `git reset --hard`, удаление, `force-push`, перезапись/миграцию больших архивов и коммиты в `main`. Не менять код игры, D16/D28/D29 и художественный канон ради раскладки.
2. Инвентаризировать отдельно: (a) новые GPT-файлы внутри `gpt_asset_library`, (b) исторические `assets/references/{hero,bosses,enemies,weapons,locations,...}`, (c) реально используемые ресурсы `game/prototype/art/`, (d) неиспользуемые тестовые/PROXY_TECHNICAL. По каждым файлам путь, роль, ID/предположение, SHA, есть ли ссылки из `.tscn/.tres/.gd` и Git статус.
3. **Автоматически раскладывать только файлы с однозначным ID и безопасным статусом** (новые локальные GPT файлы, не связанные существующими Godot-сценами). Копировать оригинал в `sources/` при наличии исходника, игровой экспорт — в `frames/` / `sprites/` и т. п.; не переписывать существующие байты без необходимости. Если имя `(1)` / `(2)`, не подменять действующий канонический путь: считать SHA и конфликт, исходное имя записать в манифест.
4. Если файл уже используется Godot по `res://...`, **не перемещать его только для красоты**. Для нового пути создать проверенную производную копию, обновлять ссылки лишь в отдельно проверяемом интеграционном шаге с реальным smoke-test; устаревшее ссылочное место сохранять до подтверждения. Старые утверждённые мастера и исторические ZIP не переносить без отдельного прямого решения владельца.
5. Создать недостающие каталоги категорий и H01 локально; положить `README` / индекс / карточки из GitHub и **фактически обнаруженные** файлы. `asset_index.json`, `asset.json`, художественный реестр, память этапа синхронизировать. Не проставлять `PUSHED` до удалённого подтверждения реального PNG в GitHub.
6. Небезопасные/неоднозначные ситуации зафиксировать списком `NEEDS_OWNER_DECISION`: конфликт ID, один ID в разных категориях, неизвестное происхождение, изменение утверждённого оригинала, файл используется сценой, разные версии с разным SHA при одном имени. Не удалять и не присваивать новый канон на своё усмотрение.
7. Проверить корректность JSON, что каждый путь из `asset_index` указывает на реально существующую карточку, `files[]` только на реально существующие PNG, SHA совпадают, направления/кадры не дублируются, пути не выходят из корня, Godot-пути не битые, а игра по-прежнему запускается. Для текущей задачи достаточно **одного** релевантного smoke-test.
8. Коммитить и пушить лишь согласованную **рабочую** ветку после проверок; в отчёте дать перемещённые/созданные пути, затронутые Godot-ссылки, SHA, нерешённые случаи и remote HEAD. **Не считать библиотеку заполненной**, если реально ещё нет PNG.
