## Как пополнять журнал

Новое решение добавляется отдельной строкой `D<n>` с датой, точной формулировкой и списком затронутых документов. Решение, меняющее прежнее, помечает старое как `SUPERSEDED` — удалять старые записи нельзя.

**Решение:** разделять три независимые оси — **статус художественного решения**, **наличие файла** и **готовность игрового ассета**. Локальное наличие, локальный коммит и публикация в GitHub учитываются отдельно.
**Нормативная таблица:** [AGENTS.md §7](../AGENTS.md). Практические значения по единицам: [CONCEPT_ART_INDEX.md](CONCEPT_ART_INDEX.md), [BESTIARY.md §0](BESTIARY.md).

### D4 — Интеграция правил · 2026-10-25 · `APPROVED`
**Решение:** безопасно интегрировать `AGENTS.md` и `docs/GITHUB_WORKFLOW.md` из `origin/main` в рабочую ветку. Локальные изменения и незавершённые файлы не перезаписывать и не терять.

### D5 — Публикация · 2026-10-25 · `SUPERSEDED` (D13)
**Решение:** **`push` запрещён**. Pull Request и merge в GitHub также запрещены. Все изменения остаются локальными до отдельного решения владельца.
**Следствия:** `AGENTS.md §2` (push/PR после подтверждения) не применяется как разрешение; используется только локальная работа и локальные коммиты.
**Статус:** ограничение действовало до D13 (2026-10-25). D13 снимает запрет **только для рабочей ветки текущего этапа**; запрет прямого push в `main`, force push, удаления истории и самостоятельного merge сохраняется.

### D12 — Межчатовая память · 2026-10-25 · `APPROVED`
**Решение:** каждый новый этап разработки начинается в **отдельном новом чате DeepSeek Harness с пресетом Rogalik Dev**. Контекст между чатами передаётся через постоянные заметки в репозитории, а не только через память модели или историю чатов.
**Обязательные артефакты:** `docs/progress/PROJECT_STATE.md` — краткое актуальное состояние; `docs/progress/STAGE_NN.md` — заметка этапа, создаётся при начале этапа (пустые журналы будущих этапов не создаются).
**Следствия:**

- новый чат обязан прочитать `AGENTS.md` → `docs/DEVELOPMENT_PLAN.md` → `docs/DECISIONS.md` → `PROJECT_STATE.md` → заметку текущего этапа, затем сверить их с Git и файлами и продолжить с последней незавершённой задачи;
- после каждой законченной задачи обновляются заметка этапа и (при существенном изменении) `PROJECT_STATE.md`, затем делается локальный коммит;
- этап нельзя начинать без приёмки предыдущего; статус `ACCEPTED` ставит только владелец;
- до окончания этапа чат можно заменить только чатом «Этап N — продолжение» с той же памятью;
- расхождение заметок с Git/файлами фиксируется как `DISCREPANCY` и выясняется причина — факты не подгоняются под память.

**Затронуто:** [AGENTS.md §8](../AGENTS.md), [DEVELOPMENT_PLAN.md §0, §2, §6](DEVELOPMENT_PLAN.md), [AI_STUDIO_PLAYBOOK.md §1, §3](AI_STUDIO_PLAYBOOK.md), каталог `docs/progress/`.

### D13 — Общий репозиторий разработки · 2026-10-25 · `APPROVED`
**Решение:** начиная с этого решения GitHub используется как **общий источник исходного кода, документации, ассетов и межчатовой памяти** для DeepSeek Harness и ChatGPT. DeepSeek Harness — главный разработчик; ChatGPT — консультант и независимый ревьюер.
**Полномочия:** `push` в **рабочую ветку текущего этапа** разрешён после завершённой и проверенной задачи. Первый push выполняется только после проверки владельцем отчёта о составе публикации.
**Запрещено:** прямой `push` в `main`, force push, удаление истории, самостоятельный merge в `main`. `main` обновляется только через согласованный владельцем Pull Request.
**Постоянный цикл:** задача → разработка → проверка → обновление памяти → локальный коммит → push в рабочую ветку. Следующий этап — новый чат (D12).
**Ревью ChatGPT:** рекомендации оцениваются самостоятельно — принимаются, изменяются или аргументированно отклоняются; утверждённый канон из-за рекомендаций не меняется.
**Следствия:**

- D5 в части запрета `push` — `SUPERSEDED`; запрет касается только рабочей ветки этапа, всё остальное (нет прямого push в `main`, нет merge агентом) действует;
- рабочая ветка `stage1-playable-combat` сохраняется, не пересоздаётся и не переписывается; `main` и `rogalik-dev` не трогаются;
- первая публикация — отдельный шаг с отчётом: файлы, объёмы бинарников, способ загрузки ZIP, исключённое ([GITHUB_WORKFLOW.md §5](GITHUB_WORKFLOW.md));
- наличие файла `PUSHED` присваивается только после проверки удалённой ветки, а не после локального коммита (D3);
- память (`PROJECT_STATE.md`, `STAGE_NN.md`, `DECISIONS.md`) обновляется в том же коммите, что и связанное изменение; синхронность проверяется `tools/git/check-memory-sync.ps1`;
- ZIP владельца и оригинальные PNG остаются в Git; Git LFS не включается, поскольку перенос уже закоммиченного 65-MB файла требует перезаписи истории.

**Затронуто:** [AGENTS.md §2, §4, §8](../AGENTS.md), [GITHUB_WORKFLOW.md](GITHUB_WORKFLOW.md), [DEVELOPMENT_PLAN.md §2, §6](DEVELOPMENT_PLAN.md), [PROJECT_STATE.md](progress/PROJECT_STATE.md), [STAGE_01.md](progress/STAGE_01.md), [AI_STUDIO_PLAYBOOK.md §3](AI_STUDIO_PLAYBOOK.md), `.gitignore`, `.gitattributes`, `tools/git/`.

**Уточнение D14 (2026-10-25):** пункты о предварительном подтверждении владельцем первой и последующих публикаций — `SUPERSEDED` решением D14. Остальные следствия D13 (общий репозиторий, `main` только через PR, проверка `PUSHED`, память вместе с работой) действуют.

### D14 — Автоматическая публикация · 2026-10-25 · `APPROVED`
**Решение:** требование предварительного подтверждения владельцем перед обычным `push` **отменено**, включая первый `push` рабочей ветки. Обычный `push` в согласованную рабочую ветку выполняется **автоматически** после успешных локальных проверок и локального коммита.
**Остаётся запрещённым:** прямой `push` в `main`, force-push, перезапись истории, обход защиты веток, самостоятельный merge в `main`. `main` — только через согласованный с владельцем Pull Request.
**Следствия:**

- решение заменяет в D13 только ограничение «сначала подтверждение, потом push»; остальное из D13 действует;
- отчёт о публикации ([reports/d13_publication_report.md](../reports/d13_publication_report.md)) сохраняется как **обязательный информационный** артефакт (что публикуется, объёмы бинарников, способ загрузки ZIP), но **не является гейтом**: push не ждёт отдельного одобрения;
- при отсутствии авторизации используется штатный механизм Git Credential Manager; отдельное разрешение на публикацию не запрашивается; токены не передаются в чат и не пишутся в репозиторий;
- если авторизацию технически выполнить нельзя — фиксируется конкретный `BLOCKER`, публикация не подменяется «локальным успехом»;
- после каждого push проверяется фактический SHA удалённой ветки (`git rev-parse origin/<ветка>`) и наличие файлов; только затем ставится `PUSHED` (D3) и обновляется память;
- ZIP владельца сохраняется, история не переписывается.

**Затронуто:** [AGENTS.md §2, §4, §8](../AGENTS.md), [GITHUB_WORKFLOW.md §2, §5, §6](GITHUB_WORKFLOW.md), [DEVELOPMENT_PLAN.md §2, §6](DEVELOPMENT_PLAN.md), [PROJECT_STATE.md](progress/PROJECT_STATE.md), [STAGE_01.md](progress/STAGE_01.md), отчёт о публикации.
