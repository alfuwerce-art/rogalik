### D12 — Межчатовая память · 2026-10-25 · `APPROVED`
**Решение:** каждый новый этап разработки начинается в **отдельном новом чате DeepSeek Harness с пресетом Rogalik Dev**. Контекст между чатами передаётся через постоянные заметки в репозитории, а не только через память модели или историю чатов.
**Обязательные артефакты:** `docs/progress/PROJECT_STATE.md` — краткое актуальное состояние; `docs/progress/STAGE_NN.md` — заметка этапа, создаётся при начале этапа (пустые журналы будущих этапов не создаются).
**Следствия:**

- новый чат обязан прочитать `AGENTS.md` → `docs/DEVELOPMENT_PLAN.md` → `docs/DECISIONS.md` → `PROJECT_STATE.md` → заметку текущего этапа, затем сверить их с Git и файлами и продолжить с последней незавершённой задачи;
- после каждой законченной задачи обновляются заметка этапа и (при существенном изменении) `PROJECT_STATE.md`, затем делается локальный коммит;
- этап нельзя начинать без приёмки предыдущего; статус `ACCEPTED` ставит только владелец;
- до окончания этапа чат можно заменить только чатом «Этап N — продолжение» с той же памятью;
- расхождение заметок с Git/файлами фиксируется как `DISCREPANCY` и выясняется причина — факты не подгоняются под память.

**Затронуто:** [AGENTS.md §8](../AGENTS.md), [DEVELOPMENT_PLAN.md §0, §2, §6](DEVELOPMENT_PLAN.md), [AI_STUDIO_PLAYBOOK.md §1, §3](AI_STUDIO_PLAYBOOK.md), каталог `docs/progress/`.

### D13 — Общий репозиторий разработки · 2026-10-25 · `APPROVED`
**Решение:** начиная с этого решения GitHub используется как **общий источник исходного кода, документации, ассетов и межчатовой памяти** для DeepSeek Harness и ChatGPT. DeepSeek Harness — главный разработчик; ChatGPT — консультант и независимый ревьюер.
**Полномочия:** `push` в **рабочую ветку текущего этапа** разрешён после завершённой и проверенной задачи. Первый push выполняется только после проверки владельцем отчёта о составе публикации.
**Запрещено:** прямой `push` в `main`, force push, удаление истории, самостоятельный merge в `main`. `main` обновляется только через согласованный владельцем Pull Request.
**Постоянный цикл:** задача → разработка → проверка → обновление памяти → локальный коммит → push в рабочую ветку. Следующий этап — новый чат (D12).
**Ревью ChatGPT:** рекомендации оцениваются самостоятельно — принимаются, изменяются или аргументированно отклоняются; утверждённый канон из-за рекомендаций не меняется.
**Следствия:**

- D5 в части запрета `push` — `SUPERSEDED`; запрет касается только рабочей ветки этапа, всё остальное (нет прямого push в `main`, нет merge агентом) действует;
- рабочая ветка `stage1-playable-combat` сохраняется, не пересоздаётся и не переписывается; `main` и `rogalik-dev` не трогаются;
- первая публикация — отдельный шаг с отчётом: файлы, объёмы бинарников, способ загрузки ZIP, исключённое ([GITHUB_WORKFLOW.md §5](GITHUB_WORKFLOW.md));
- наличие файла `PUSHED` присваивается только после проверки удалённой ветки, а не после локального коммита (D3);
- память (`PROJECT_STATE.md`, `STAGE_NN.md`, `DECISIONS.md`) обновляется в том же коммите, что и связанное изменение; синхронность проверяется `tools/git/check-memory-sync.ps1`;
- ZIP владельца и оригинальные PNG остаются в Git; Git LFS не включается, поскольку перенос уже закоммиченного 65-MB файла требует перезаписи истории.

**Затронуто:** [AGENTS.md §2, §4, §8](../AGENTS.md), [GITHUB_WORKFLOW.md](GITHUB_WORKFLOW.md), [DEVELOPMENT_PLAN.md §2, §6](DEVELOPMENT_PLAN.md), [PROJECT_STATE.md](progress/PROJECT_STATE.md), [STAGE_01.md](progress/STAGE_01.md), [AI_STUDIO_PLAYBOOK.md §3](AI_STUDIO_PLAYBOOK.md), `.gitignore`, `.gitattributes`, `tools/git/`.

### D14 — Автоматическая публикация · 2026-10-25 · `APPROVED`
**Решение:** требование предварительного подтверждения владельцем перед обычным `push` **отменено**, включая первый `push` рабочей ветки. Обычный `push` в согласованную рабочую ветку выполняется **автоматически** после успешных локальных проверок и локального коммита.
**Остаётся запрещённым:** прямой `push` в `main`, force-push, перезапись истории, обход защиты веток, самостоятельный merge в `main`. `main` — только через согласованный с владельцем Pull Request.
**Следствия:**

- решение заменяет в D13 только ограничение «сначала подтверждение, потом push»; остальное из D13 действует;
- отчёт о публикации ([reports/d13_publication_report.md](../reports/d13_publication_report.md)) сохраняется как **обязательный информационный** артефакт (что публикуется, объёмы бинарников, способ загрузки ZIP), но **не является гейтом**: push не ждёт отдельного одобрения;
- при отсутствии авторизации используется штатный механизм Git Credential Manager; отдельное разрешение на публикацию не запрашивается; токены не передаются в чат и не пишутся в репозиторий;
- если авторизацию технически выполнить нельзя — фиксируется конкретный `BLOCKER`, публикация не подменяется «локальным успехом»;
- после каждого push проверяется фактический SHA удалённой ветки (`git rev-parse origin/<ветка>`) и наличие файлов; только затем ставится `PUSHED` (D3) и обновляется память;
- ZIP владельца сохраняется, история не переписывается.

**Затронуто:** [AGENTS.md §2, §4, §8](../AGENTS.md), [GITHUB_WORKFLOW.md §2, §5, §6](GITHUB_WORKFLOW.md), [DEVELOPMENT_PLAN.md §2, §6](DEVELOPMENT_PLAN.md), [PROJECT_STATE.md](progress/PROJECT_STATE.md), [STAGE_01.md](progress/STAGE_01.md), отчёт о публикации.

Проверки разделяются: пиксельная чёткость базовых ассетов, визуальная корректность динамического света, производительность. Плавное динамическое освещение может содержать цветовые переходы, не подчиняющиеся строгой проверке однородности блоков 2×2.

### D22 — Полноценное художественное производство и `ART_PRODUCTION_GATE` · 2026-10-26 · `APPROVED`
**Решение:** владелец **не принимает** текущий уровень художественного исполнения Rogalik и **меняет порядок художественной разработки**. Технические задачи 3.1–3.1d доказали возможность работы спрайтов, Godot, Pixelorama, анимационных кадров, динамического света и теней, но созданный герой существенно отличается от утверждённого образа, а графика в целом не приближается к целевому уровню.

**Главное правило.** Полноценное производство анимаций персонажа начинается **только после утверждения** художественного эталона, исходного разрешения спрайта, ракурса и **воспроизводимого способа изготовления графики**. Правило распространяется на героя, врагов, боссов и другие анимируемые объекты.

**Разделение двух независимых направлений работы:**

1. **TECHNICAL DEVELOPMENT** — разрешено всегда: управление, контроллер состояний, переходы `idle / move / dodge / attack / hurt / death`, коллизии, хитбоксы, взаимодействие с оружием, движение и рывки, тестирование механики на временных ассетах, архитектура импорта и воспроизведения анимаций. Временные ассеты имеют статус **`PROXY_TECHNICAL`**. **Технически готовая анимационная система не означает, что художественные кадры анимации готовы.**
2. **ART PRODUCTION** — художественно убедительный базовый образ → утверждённый исходный размер спрайта → утверждённый игровой ракурс → палитры, материалы, способ освещения → редактируемый мастер-ассет → проверка в реальной игре → **художественная приёмка владельца** → только затем остальные направления и анимационные состояния. **Запрещено подменять художественную разработку техническими прототипами.**

**Новый обязательный контроль `ART_PRODUCTION_GATE`** (действует совместно с D20 и `REFERENCE_FIDELITY_GATE`, не заменяя их). Полноценное производство анимаций допускается только при выполнении **всех** условий:

1. внешность соответствует утверждённому референсу;
2. художественный ракурс согласован с камерой игры;
3. исходное разрешение спрайта утверждено владельцем;
4. силуэт, анатомия и материалы художественно убедительны;
5. существует редактируемый исходник ассета;
6. способ производства позволяет получать согласованные изображения одного персонажа в разных позах;
7. спрайт успешно интегрирован в Godot;
8. владелец утвердил базовый художественный образ.

Если хотя бы одно критически важное условие не выполнено — **полный комплект художественных анимаций не начинается**; техническое программирование продолжается на `PROXY_TECHNICAL`. **Не требовать финальной графики всей игры перед разработкой механик:** правило применяется к художественному производству конкретных персонажей и объектов.

**Способ производства.** Прежний способ (Python, SDF, геометрические примитивы, параметрические формы) **перестаёт быть единственным способом создания финальной графики**: четыре последовательные итерации художественных улучшений (3.1, 3.1a, 3.1b, 3.1c/3.1d) не решили проблему. Прежние генераторы **не удаляются** и остаются пригодными для технических прототипов, масок, коллизий и вспомогательных операций. Нужно построить полноценный художественный производственный процесс.

**Целевая цепочка:** утверждённый референс → художественный мастер-образ → редактируемый ассет → пиксельная адаптация → игровая интеграция → визуальная приёмка → анимации.

**Требование к инструментам.** Перед выбором метода необходимо **фактически проверить** возможности доступных инструментов (Godot и действующий MCP, Pixelorama за пределами CLI, Krita, Blender как вспомогательный инструмент 2D-спрайтов, бесплатные редакторы Pixel Art, MCP-интеграции, программное управление редакторами) и определить для каждого: позволяет ли агенту создавать и редактировать изображения, работает ли локально, управляем ли автоматически, сохраняется ли редактируемый исходник, помогает ли сохранять узнаваемость при смене позы, совместим ли с Godot, бесплатен ли, какие имеет ограничения. **Наличие программы не является доказательством способности агента управлять ею** — проверяются фактические операции. Установка сторонних исполняемых компонентов, изменение профиля Harness, платные модели и расход API — только после **отдельного разрешения владельца**. Не устанавливать всё подряд.

**Главный критерий (`REFERENCE_FIDELITY_GATE` сохраняется отдельно).** Вопрос приёмки: **если поставить игровой кадр Rogalik рядом с его собственным концептом и качественной пиксельной графикой Children of Morta, приближается ли художественное исполнение к поставленной цели?** Использование пикселей, правильных объектов и утверждённой палитры **не является** достаточным результатом. ### D23 — Покадровый рисунок, нейтральный базовый спрайт и проверка гибридного света · 2026-10-26 · `APPROVED`

**Решение владельца:**

1. **Основные анимации персонажей, врагов и боссов — рисованные покадровые 2D Pixel Art.** Форма огня, рябь воды, трава и ткань/знамёна также преимущественно рисуются по кадрам; то, что Godot делает качественнее без дополнительных кадров (движение, мерцание, дым/туман, прозрачность, локальный свет/тени, вспомогательные FX), можно поручать движку. Никакого требования, что *всё* анимируется исключительно кадрами.
2. **Blender пока не используется для анимации.** Вернуться к нему только по новому решению владельца; отдельные установки/платные инструменты также требуют разрешения.
3. **Базовый художественный спрайт** героя, избы, телеги, бочки и других объектов рисуется с убедительными формами, материалами и нейтральной **внутренней светотенью**, но **без запечённой зависимости от конкретного динамического факела**. Один и тот же PNG потом освещает Godot: холодная общая ночь, локальные тёплые источники, отбрасываемые 2D-тени. `PointLight2D` не знает физическую 3D-форму по PNG; Normal Map — возможный дополнительный эксперимент, не массовое обязательство.
4. **Поэтапная проверка художественного пайплайна:** сначала **один высококачественный мастер-образ главного героя** (без массовых анимаций); после **художественного утверждения владельцем и прохождения D22 `ART_PRODUCTION_GATE`** — ограниченная покадровая проба `idle` и `move`; затем **тестовые объекты** бочка, телега и факел (с покадровым огнём). На том же наборе ассетов в одной сцене сравнить **A:** нейтральное освещение, **B:** общая холодная ночь, **C:** та же ночь плюс динамический тёплый факел и тени. Сделать реальные игровые кадры и клип движения, оценить читаемость и пиксельную чёткость, выбрать способ после просмотра владельцем.
5. **Объекты бочка/телега/факел на этой стадии — калибровочные**, а не новое утверждение состава или финальной «Проклятой слободы» (D10). Не менять D16, D20, D22, порядок этапов 0–6 и `main`. В **следующем чате** начать с **героя**, не с Blender, освещения или массового производства. Игровые арты/анимации пока не созданы.

### D24 — ChatGPT создаёт весь художественный Pixel Art; DeepSeek технически интегрирует · 2026-11-01 · `APPROVED`

**Прямое решение владельца (01.11.2026).** Вся новая художественная графика Rogalik создаётся **непосредственно в ChatGPT инструментом генерации/редактирования изображений**. Это относится к персонажам (герой, враги, боссы), оружию, объектам, декорациям, текстурам, тайлам/тайлсетам, интерфейсу, изображениям VFX и **каждому художественному кадру покадровых анимаций** (персонажи, огонь, вода, растения, ткань и др.). Художественные исправления и новые позы также выполняются в ChatGPT по визуальному мастер-образу. Промпт сам по себе не считается созданным изображением.

**Обязанности.**
1. **ChatGPT — автор изображений и художественный контролёр:** получает актуальный утверждённый референс и исходное изображение, генерирует мастер/варианты/кадры, сравнивает идентичность и передаёт отдельные файлы-кандидаты с ID и параметрами. 2. **DeepSeek Harness — разработчик и интегратор:** принимает фактически доступные PNG/кадры, сохраняет источники, делает техническую подготовку (прозрачность, размер без разрушения рисунка, pixel-grid, crop с полями, единый canvas/pivot, нарезка, сборка атласа, формат `.pxo`/метаданные), подключает TileSet/TileMap, SpriteFrames, VFX/свет и игровые механики в Godot, проверяет реальную сцену и публикует артефакты/память в рабочую ветку GitHub.
3. DeepSeek **не создаёт и не перерисовывает финальные художественные изображения** средствами Python/Pillow, SDF, примитивов, рисованием в Pixelorama или иной нейросетью; не исправляет анатомию, силуэт или стиль техническим ресайзом. Исторические скрипты остаются в репозитории для воспроизводимости старых опытов, технических масок и `PROXY_TECHNICAL`; не применять их для нового финального арта. Допустима обработка пикселей, не меняющая художественный замысел, а также процедурные движения, освещение и технические эффекты Godot **на базе графики GPT**.
4. При заметном художественном расхождении, дрейфе внешности, несогласованных кадрах или отсутствии нужного рисунка DeepSeek оформляет точный запрос на **новую генерацию/редактирование в ChatGPT**, а не рисует замену сам.
5. **Передача не автоматизирована:** GPT-изображение необходимо реально сохранить и передать в рабочую папку DeepSeek либо опубликовать доступным согласованным способом. Запись о файле в чате, промпт или ссылка на невыложенный локальный файл не равны переданному ассету. Генератор ChatGPT **не гарантирует** прозрачность, true pixel art, конкретные пиксельные размеры, бесшовность тайлов и идентичность кадров автоматически: нужны технические и художественные проверки, при необходимости повторная генерация. **Обязательная цепочка в самом чате GPT:** (1) использовать актуальный утверждённый мастер-референс изображением; (2) создать художественный рисунок конкретной позы/объекта без фона/интерфейса; (3) **с помощью доступных файловых/Python-инструментов самостоятельно** сделать технический игровой экспорт (настоящая альфа RGBA, художественно корректный размер на пиксельной сетке D16, холст и pivot, сохранение отдельных PNG); (4) программно измерить файл, визуально проверить читаемость в целевом игровом масштабе, исправить или перегенерировать при провале; (5) выдать ссылки на **реально существующие проверенные PNG** и, для серии, метаданные/ZIP. Если конкретная операция невозможна или файл не выдерживает тест — сообщить `NOT_GAME_READY`, **не** выдавать красивый арт за игровой спрайт.

**H01 (D25):** для одного кадра по умолчанию `H01_idle_down_000.png` (вниз экрана, three-quarter top-down), персонаж высотой **48 игровых px по альфа-силуэту**, общий canvas с прозрачными полями и измеренной точкой опоры стоп; без окружения, подписи, встроенного оружия и запечённой тени от земли/факела. Согласованный чёрно-золотой образ сохранять. Ширина canvas и координаты pivot не придумываются: фиксируются по реальному экспорту. Прямое уменьшение иллюстрации, уничтожающее лицо/повязку/вышивку, НЕ `PASS`; рисунок адаптируется художественно в ChatGPT к малому масштабу.

**Анимация:** после D22-гейта все художественно разные кадры генерирует ChatGPT, **каждый** получает отдельный PNG, общий неизменный canvas/pivot/масштаб/ориентацию и упорядоченный JSON-манифест (кадры, направление, pivot, master SHA, фактический FPS при утверждении, статусы). Лист/GIF — только дополнительное превью, не замена кадров. Для тайлов — сетка 24 игровых px и проверка стыков; для объектов — прозрачный PNG и точка опоры; для VFX — отдельные RGBA-кадры/слои и метаданные, когда нужны.

**Три независимые проверки:** `TECHNICAL_EXPORT_PASS` — реальный декодируемый PNG, альфа, пиксельный размер, canvas/pivot и необходимые файлы подтверждены; `GODOT_PASS` — DeepSeek импортировал и реально запустил сцену; `ART_APPROVED` — художественная приёмка владельца. Никогда не заменять одну другой. Если Godot не запущен в чате — честно `GODOT_NOT_TESTED`. DeepSeek продолжает заниматься интеграцией, но **не принимает на себя первичное изготовление игрового PNG за GPT**.

**Приоритет:** это ужесточение **формата выдачи по D24/D25**, а не изменение D16, D20, D22, D23, игровой схемы, художества или защиты `main`. Новый H01 уже визуально утверждён по D25, поэтому нельзя начинать запрос на игровой спрайт с повторного концепт-листа.

**Регламенты:** [AGENTS.md](../AGENTS.md), [SPRITE_ANIMATION_STANDARD.md](SPRITE_ANIMATION_STANDARD.md), [ART_ANIMATION_LIGHTING_WORKFLOW.md](ART_ANIMATION_LIGHTING_WORKFLOW.md), [PROJECT_STATE.md](progress/PROJECT_STATE.md), [STAGE_03.md](progress/STAGE_03.md); закреплённые источники ChatGPT — `инструкция.txt`, `ROGALIK_SPRITE_ANIMATION_STANDARD.txt` должны быть заменены владельцем на редакции D26.

### D27 — Контроль фактических пикселей, альфа-маски и игрового ракурса · 2026-11-01 · `APPROVED`

**Решение владельца:** исправить повторяющиеся недостатки генерации игровых изображений GPT и закрепить проверки **до** выдачи как `GAME_EXPORT`. Это дополнение к D26, а не новая стилистика или изменение D16/D25.

**Подтверждённый диагностический пример:** предоставленный владельцем большой H01 PNG — 1199×1312 RGBA; реальный силуэт по `alpha>=16`: bbox (368,227)-(827,1076), **459×849 px**, а по любому `alpha>0`: (0,19)-(1138,1256), **1138×1237 px**. **916** почти невидимых ненулевых альфа-пикселей находятся вне тела с `alpha>=16` (вне этого bbox); всего ~**0,19%** видимых пикселей (`alpha>=16`) полностью непрозрачны (`alpha=255`), основная часть близка к 253. Простое PNG RGBA + углы alpha=0 не доказывает чистую маску. При прямом понижении до 48 px теряются мелкие детали; изображение кажется главным образом фронтальным, что не подтверждает `three-quarter top-down`. Числа относятся к **конкретному диагностическому исходнику**, не являются общими порогами всех артов.

**Обязательное правило подготовки каждого игрового спрайта GPT:**
1. Сначала **входной контракт**: тип (`sprite/tile/object/vfx/frame`), точный визуальный мастер как изображение, игровая высота/размер D16, ориентировка в игровом пространстве, поза, желаемые прозрачность и опорная точка. `DOWN` значит смотреть к нижнему краю экрана **при камере сверху под углом**, а не портрет в фас на уровне глаз. Не подменять конкретный исходный PNG названием файла или описанием.
2. **Художественная адаптация в целевом пиксельном разрешении**: сначала проверить читаемость силуэта, повязки, рубахи и отличительных черт на 48 игровых px, не только на увеличении. Если механическое уменьшение уничтожает форму/цветовые зоны/золотую вышивку — `VISUAL_FAIL`; исправлять пиксельное изображение в ChatGPT, не менять D16 и не выдавать уменьшенную иллюстрацию за `PASS`. Уменьшение nearest лишь сохраняет резкость, **не добавляет** нужную информацию и не исправляет ракурс.
3. **Строгий alpha-QA для обычного непрозрачного персонажа:** проверять два bbox (любой alpha>0 и надёжный alpha>=16), размеры, реальное число/долю пикселей alpha=255, полупрозрачные края, шум/островки вдали от фигуры и касание краёв canvas. Даже если угловые пиксели alpha=0, невидимый мусор может расширять bbox. При найденных артефактах — `NOT_GAME_READY`, очистить их без удаления художественных частей и перепроверить. Для художественно полупрозрачных VFX/тумана/дыма — **отдельный профиль**, нельзя применять требование сплошной непрозрачности к ним.
4. **Пиксельная сетка и масштаб:** проверить фактическую фигуру именно в **48 px** (для H01), PNG RGBA с alpha=0 снаружи, без сглаживания/мыла, без нарисованных тени и земли, без пустых огромных полей; фиксировать по факту canvas и pivot. Не делать `PASS` по разрешению исходника генератора. Отдельно 1× в логической сцене 480×270 и 2× nearest в 960×540 или их честный файл-макет для чтения; реальный Godot-скрин отдельно.
5. **Художественный ракурс проверяется визуально:** видны верхние плоскости головы и плеч, при этом тело/ноги читаются в top-down логике, перспектива согласована с локацией. `DOWN` не равен «фронтально, на уровне глаз». Не делать `YES` автоматически по текстовому промпту.
6. **Покадровая устойчивость:** общий canvas, pivot/root, масштаб головы/плеч/пояса, наряд, тон одежды и символ вышивки, отсутствие плавания фигуры и изменения внешности; базовая поза и один пробный кадр до полного цикла. Увеличенное PNG и общий лист — только превью. Каждый художественный кадр делается в GPT.
7. **Раздельная приёмка:** программа `tools/art/validate_game_export.py` даёт лишь `TECHNICAL_EXPORT_PASS/NOT_GAME_READY`; отдельно `VISUAL_GAME_SCALE_REVIEW` и `REFERENCE_FIDELITY_GATE`; Godot подтверждается только запуском и реальным кадром `GODOT_PASS`, художественно утверждает только владелец. Ссылки на реально проверенные итоговые PNG и числовой отчёт обязательны. Если провести проверку невозможно — `NOT_VERIFIED`, не `PASS`.

**Следствия:** новый H01 D25 **не нужно перерисовывать как концепт**. Следующий художественный продукт — из мастера создать **один** пригодный `H01_idle_down_000.png`, а не отдельный увеличенный портрет; лишь затем тест одной позы/переходов и серийная анимация по D22. Для иных объектов — применять QA по их природе (например, тайлы проверять на швы и сетку 24 px; эффекты проверять на альфа-слои), не ставить всему универсальные 48 px.

**Затронуто:** [AGENTS.md](../AGENTS.md), [SPRITE_ANIMATION_STANDARD.md](SPRITE_ANIMATION_STANDARD.md), [ART_ANIMATION_LIGHTING_WORKFLOW.md](ART_ANIMATION_LIGHTING_WORKFLOW.md), [PROJECT_STATE.md](progress/PROJECT_STATE.md), [STAGE_03.md](progress/STAGE_03.md), [ART_ASSET_ANIMATION_REGISTRY.md](ART_ASSET_ANIMATION_REGISTRY.md), [validate_game_export.py](../tools/art/validate_game_export.py), два закреплённых TXT источников ChatGPT. Исторические D16/D20/D22–D26 не переписываются, `main` не затрагивается.

### D28 — высокодетализированная игровая графика вместо принудительных 48px исходника · 2026-11-01 · `APPROVED_DIRECTION / HD4X_PILOT`

**Один источник технической истины на пилоте:** [HD_ART_PRODUCTION_PROFILE.md](HD_ART_PRODUCTION_PROFILE.md) и [`config/art_profiles/hd4x_pilot.json`](../config/art_profiles/hd4x_pilot.json). Если исходный профиль неизвестен — **не придумывать размеры** и не выдавать иллюстрацию за `GAME_EXPORT`.

**Контракты по типам:** H01 = один `H01_idle_down_000.png` высотой **192px видимого тела** под HD4X, RGBA, прозрачный фон, подтверждённый top-down, измеренные canvas/pivot. Тайлы = **96px** на мировую клетку 24, швы и атлас проверены. Оружие отдельное с grip-point. VFX — отдельные PNG и anchor/emitter со своими требованиями к прозрачности. Анимации — каждый художественный кадр создаёт ChatGPT; единый master, один согласованный pixel density, canvas/pivot внутри клипа, непрерывность поз, JSON-манифест. Существующий D22-гейт серийной анимации сохраняется.

**Обязательное доказательство:** GPT создаёт отдельные реальные игровые PNG, а не декоративный лист; измеряет alpha/bbox/плотность, фиксирует `profile_id`, SHA, canvas, pivot и манифест; проверяет настоящее качество при **192px и 1920×1080**, не по 48px. Списки проверок D26/D27 сохраняются, **но их целевое число 48 относится к D16-экспорту и не должно ошибочно применяться к HD4X**. Технический PASS, Godot PASS и художественная приёмка остаются раздельными. DeepSeek получает готовый PNG, собирает/тестирует сцену, не рисует художественный контент.

**Следующая работа:** художественный мастер H01 D25 уже выбран. GPT: один HD4X игровой экспорт `H01_idle_down_000.png` высотой 192px; DeepSeek: отдельная тестовая сцена без замены D16, тест 1920×1080 с 96px тайлом/одним объектом и реальным сравнением с текущим видом, затем решение владельца по окончательному художественному профилю. **Никаких массовых анимаций до D22.** `main` не затрагивать.

### D29 — восьминаправленный герой: 4 стороны + 4 диагонали · 2026-11-01 · `APPROVED_REQUIREMENT / PILOT`

**Последнее прямое решение владельца:** игровые персонажи должны смотреть **в восемь направлений**, а не только четыре. Существующие контроллеры 4-direction остаются временными до отдельной интеграции, не выдаются за выполненный 8-direction.

**Порядок генерации без преждевременного тиражирования:** **сначала один** проверяемый `H01_idle_down_right_000.png` в пилотном HD4X — видимое тело **192 исходных px**, true RGBA alpha, `three-quarter top-down`, чёрно-золотой H01 D25. При виде со спины не рисовать сквозь ткань видимые глаза/переднюю вышивку.

**Критерии:** `TECHNICAL_EXPORT_PASS` только после QA пикселей/alpha/bbox/масштаба, `VISUAL_GAME_SCALE_REVIEW` отдельно по ракурсу и узнаваемости, `GODOT_PASS` только после реальной игры, `ART_APPROVED` только владелец. D22 по серийным анимациям сохраняется; первая диагностическая поза до полного гейта разрешена. Профиль [HD4X](HD_ART_PRODUCTION_PROFILE.md), данные [JSON](../config/art_profiles/hd4x_pilot.json). По D28 разрешение 192px/тайл 96px **пилотное**, не автоматически финально утверждённое владельцем.

Не добавлять несуществующие кадры в `files`, не считать наличие записи фактом импорта.

**Разделение библиотека/игра:** `assets/references/gpt_asset_library/` — общая **библиотека входных оригиналов и подготовленных экспортов**, а `game/prototype/art/` (или соответствующий путь текущей Godot-сцены) — производные **интегрированные** игровые ресурсы. DeepSeek ищет ассеты по ID и манифесту, сверяет существование/SHA/статусы, переносит в Godot только реальные допустимые файлы, обновляет оба JSON и художественный реестр. Сам художественный контент создаёт GPT (D24); DeepSeek не перерисовывает финальное изображение.

**Наличие:** при учреждении D30 в GitHub созданы **только README, индекс, шаблон и карточка H01 с `NOT_IMPORTED`**. Изображение H01 от пользователя не загружено/не проверено данным действием. Запись про файл не равна настоящему PNG или `PUSHED`; передача из ChatGPT на ПК DeepSeek не автоматизирована. Нет оснований отмечать восемь направлений, анимации и Godot как готовые.

**Не меняются:** D16 (кроме уже изменённых D29 направлений), D20, D22–D29, действующий геймдизайн, статус этапа, защищённая `main` и исторические пути ранее загруженных источников. Библиотека вводит **хранение и автоматический поиск**, не новый художественный канон и не приёмку ассетов.
