## 0. Правила учёта и чтения статусов

**Разделять четыре независимых вопроса:**
1. **Состав:** ROSTER_APPROVED (существо/семейство/вид оружия принято), PROPOSED (элемент предложен), либо NOT_SPECIFIED. Включение в состав **не означает** утверждения визуала или анимаций.
2. **Визуал:** VISUAL_APPROVED (есть утверждённый референс), VISUAL_CANDIDATE (кандидат), NO_REFERENCE (блокер художественного производства), LOOK_REFERENCE (ориентир, не канон).
3. **Игровая готовность:** NONE (нет финального игрового ассета), PROXY_TECHNICAL, ASSET_DRAFT, ASSET_APPROVED (только после приёмки владельцем).
4. **Фактическое исполнение:** TODO / TECH_PASS / PARTIAL / NEEDS_REVIEW / BLOCKED_NEEDS_REFERENCE / DONE. DONE не присваивать без пути к артефакту, доказательства проверки и утверждения, если оно требуется.

**Обязательные поля при обновлении строки:** ID; тип; референс / источник; запрошенные спрайты или анимации; статусы по четырём осям; актуальный путь к исходнику/PNG/сцене; игровой кадр/клип; ветка и SHA; дата и нерешённый вопрос. Нельзя отмечать строки выполненными после одной генерации картинки или одного технического теста.

**Жёсткий гейт D22:** анимационное художественное производство по персонажу допускается только после успешного ART_PRODUCTION_GATE: эталон, размер, ракурс, способ получения одинакового качества, редактируемый исходник, интеграция и утверждение владельца. До этого возможны только PROXY_TECHNICAL и ограниченная проверка метода. Промежуточные кадры не являются утверждёнными анимациями.

**Пожелание владельца в текущем обсуждении:** целевой вид анимации — **покадровая 2D Pixel Art**; можно использовать Blender/2D-скелеты как **вспомогательные** средства для поз, но итоговые кадры оцениваются как пиксельный арт. Это не означает одобрение Blender к установке или прохождение D22.

**Зафиксированные константы D16:** тайл 24 px, герой 48 px, четыре направления, zoom 1.0, viewport 480×270, окно 960×540. Вариант героя 96 px — эксперимент, не утверждён как производственный.

**Источники:** [бестиарий](BESTIARY.md), [боссы](BOSS_REFERENCES.md), [герой](HERO_REFERENCE.md), [оружие](WEAPON_REFERENCES.md), [способности](SKILLS_AND_BOONS.md), [индекс концептов](CONCEPT_ART_INDEX.md), [арт-дирекция](ART_DIRECTION.md), [концепт первой локации](FIRST_LOCATION_CONCEPT.md), [правила локации](FIRST_LOCATION_ART_RULES.md), [план разработки](DEVELOPMENT_PLAN.md), [правила качества](PIXEL_ART_STYLE_GUIDE.md), [глобальные проходы](GLOBAL_ASSET_PASSES.md).

## 9. Как обновлять реестр по мере готовности

1. В начале художественной задачи найти ID здесь; сверить его с первичным документом, текущим решением, реальным файлом и веткой. **Не стартовать сразу всё из списка.**
2. Утверждение **состава**, **визуала**, **клипа**, **интеграции** и **владельцем** записывать отдельно. Менять статусы только после подтверждения соответствующей оси.
3. Для сделанного записать: ID → исходник (.pxo, при использовании Blender также .blend) → экспорт PNG/атлас → сцена Godot → фактический скрин/видео → Gate → коммит SHA. Для неутверждённых идей сохранять PROPOSED/HOLD.
4. После небольшого завершённого блока обновить соответствующие строки и прогресс [PROJECT_STATE.md](progress/PROJECT_STATE.md) + [STAGE_03.md](progress/STAGE_03.md) (либо заметку текущего этапа), сделать проверенный commit и обычный push в активную ветку; **main защищена**.
5. Не удалять строки завершённой работы: менять статус и прикреплять доказательство, чтобы следующая сессия не делала её повторно. Не менять правила D16/D20/D22, статус локации D10 и утверждения референсов без нового решения владельца.
