# Пакетная разработка всех моделей и анимаций — обязательный порядок для DeepSeek

> Утверждение владельца: **не доводить одну модель до финала, пока остальные персонажи отсутствуют; проходить одну производственную стадию сразу по всему утверждённому составу.** Этот документ имеет приоритет над формулировками о «полировке по одной модели» из старых инструкций. План, не подтверждение уже выполненной работы.

## 1. Что значит «все модели»

**Состав берётся из [BESTIARY.md](BESTIARY.md):** 9 боссов, 10 семейств обычных врагов, плюс главный герой и согласованные варианты каждого семейства. Повторяющиеся элементы считаются отдельными визуальными моделями, если различаются силуэтом/оружием/анимациями. Разновидности Мёртвого стрелка с неутверждённым визуалом могут существовать как помеченные `PROXY/CANDIDATE` до решения владельца.

Также отдельными общими пакетами обрабатываются оружие, архитектурные комплекты первой локации и природные объекты. Объём будущих локаций не расширять самовольно: полный круг только по текущему утверждённому production scope. **Отсутствие рисунка не блокирует честный технический proxy, но запрещает финальную художественную приёмку.**

## 2. Строгая глобальная очередность

**M0 — Инвентаризация всех моделей.**
- Сделать таблицу модели/семейства/варианта/сценария движения/рига/источника референса/одобрения.
- Зафиксировать `TODO`, `PROXY`, `NEEDS_REFERENCE`, `BLOCKED`; ничего не выдавать за уже созданное.
- Один-два **коротких технических эталона** для проверки импорта, скелета, камеры и движения, затем возвращаемся к общей очереди. Эталон не полируется до финала.

**M1 — Грубая геометрия ДЛЯ ВСЕХ.**
- Каждый вид/утверждённая разновидность получает читаемый blockout: силуэт, размеры, крупное оружие и коллизию. Отдельные грубые комплекты декора и архитектуры.
- Не тратить время на лица, ржавчину, мех, ткани, волосы и богатые материалы.
- GATE для перехода: матрица подтверждает, что у всех моделей текущего пакета есть игровой proxy либо формальный блокер/явно исключённый scope; изображения с настоящей игровой камеры.

**M2 — Базовые скелеты ДЛЯ ВСЕХ.**
- Классифицировать humanoid/heavy humanoid/quadruped/creature; переиспользовать проверенные совместимые риги.
- Отдельный риг для уникальных тел (трёхголовый Горыныч и др.).
- Проверять суставы/веса, оружейные сокеты, деформации, показательные позы. Не переходить к M3, пока группа не проверена.

**M3 — Базовые анимации ДЛЯ ВСЕХ.**
- Idle, locomotion, turn, attack windup-hit-recovery, hit reaction, death; специальные движения — если нужны типу врага.
- Сначала лицензированные качественные клипы + retarget, затем недостающие черновые движения. Никогда не превращать человека в анимацию волка.
- GATE: каждый прототип воспроизводимо движется, а атаки читаются на игровом расстоянии; видео/кадры, минимальные тесты.

**M4 — Поведение и игровой тест ВСЕГО СОСТАВА.**
- На общей тестовой арене каждый тип демонстрирует свою боевую роль, без фиктивного утверждения чисел урона/фаз.
- Проверка с несколькими врагами одновременно, коллизии, попадания, производительность, переходы анимаций.
- По итогу законченного блок-аута ВСЕХ становится понятен реальный объём игры.

**M5 — Детализация моделей ВСЕХ.**
- По кругу, не по одному до финала: сначала крупные формы/броня/одежда у всех → затем лица/аксессуары у всех → затем материалы/текстуры у всех.
- Не пытаться шлифовать незатверждённый референс; держать его `NEEDS_REVIEW`.
- После каждой категории краткая визуальная проверка на игровой камере, без блокирования работы по другим исправным ассетам.

**M6 — Полировка анимаций ВСЕХ.**
- По общим группам ригов: перенос веса, контакт ступней, blend, инерция оружия, hit windows, IK, уникальная пластика; сравнение видео до/после.
- Сначала устранить системные дефекты общих движений, чтобы не исправлять их по отдельности десятки раз.

**M7 — Общая интеграция, VFX, звук и финальные проверки.**
- Проход всей локации со смешанным составом врагов; проверка камеры, боевой читаемости, fps на целевом ПК, ошибок и регрессий.
- Художественная приёмка владельцем по группам; `RELEASE_CANDIDATE` только с проверяемой сценой и клипами.

**Правило приоритета:** `M0 → M1(все) → M2(все) → M3(все) → M4(все) → M5(все) → M6(все) → M7(все)`. **Запрещён маршрут** `M1-E01 → M7-E01 → M1-E02`. Допустимые исключения: короткий пилот (не финальный арт); технический блокер с прозрачной записью и продолжение остальных; отдельная неизбежная задача для движка.

## 4. Контрольные ворота для всей группы

До переключения на следующий этап DeepSeek предъявляет:
1. Название текущей стадии и полный список единиц на ней.
2. Сколько реально завершено/проверено из общего числа и сколько остались `BLOCKED/NEEDS_REVIEW`.
3. Скриншоты общего lineup на игровом масштабе и тестовый билд или воспроизводимый скрипт.
4. Короткие видео движения и атак для каждого **типа рига и ключевой роли**, плюс индивидуальные записи нетипичных боссов.
5. Список исправленных дефектов и оставшихся рисков.
6. Подтверждение, что следующая стадия не начинается при скрытых незавершённых элементах. Исключение требует явного решения владельца или согласованного временного proxy, не подменяющего финальную работу.

**Каждую мелочь не гонять через глобальный длительный тест:** быстрые локальные проверки после изменений, пакетный интеграционный gate по окончании стадии.

## 5. Работа в репозитории

- Отдельные задачи внутри одной общей стадии (`MODEL-BLOCKOUT-E01`, `MODEL-BLOCKOUT-E02`...) с обобщающей карточкой рубежа `M1-GATE`.
- Хранить полезный прототип и статус каждого объекта в репозитории; Git LFS для бинарных игровых ассетов после настройки.
- Следующая сессия DeepSeek читает текущую стадию и таблицу охвата, **продолжает с незавершённых элементов**, а не начинает заново.
- Отдельные `PROPOSED` концепты первой локации не превращать молча в финальные локации без согласования владельцем.
