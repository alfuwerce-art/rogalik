# GitHub — общий репозиторий разработки Rogalik

> Статус 2026-10-25 (ред. 4, решения **D13 + D14**): GitHub — общий источник кода, документации, ассетов и межчатовой памяти для DeepSeek Harness и ChatGPT. Обычный `push` в **рабочую ветку текущего этапа** выполняется **автоматически** после проверенной задачи и локального коммита — предварительное подтверждение владельцем не требуется (D14). Прямой `push` в `main`, force push, удаление истории, обход защиты веток и самостоятельный merge в `main` запрещены. Защита `main` настроена владельцем (D11) — повторно не настраивать.
> Отчёт о публикации — обязательный **информационный** артефакт (§5), а не гейт: push не ждёт одобрения.

## 2. Полномочия (D13, D14)

**Разрешено и выполняется автоматически:**
- читать репозиторий, править рабочую копию, запускать проверки и делать локальные коммиты;
- `push` в **рабочую ветку текущего этапа** после завершённой и проверенной задачи, когда память обновлена и сделан коммит — **без предварительного подтверждения владельца**, включая первый push ветки (D14);
- сообщать владельцу ветку и SHA каждого push.

**Запрещено:**
- прямой `push` в `main`, force push, удаление ветки, перезапись опубликованной истории, обход защиты веток;
- самостоятельный merge в `main` (сливает владелец после согласованного Pull Request);
- `push` в чужие ветки/репозитории, публикация секретов и `.env`;
- `git reset --hard`, `git clean -fdx`, массовое удаление и переименование без ясного разрешения.

**Только по согласованию владельца:** создание Pull Request, изменение настроек репозитория, любые действия с `main`, публикация за рамками рабочей ветки этапа.

**ChatGPT — консультант и независимый ревьюер.** Его рекомендации по публикации оцениваются самостоятельно: принять, изменить или аргументированно отклонить. Канон (D1–D14) из-за рекомендаций не меняется.

## 3. Ветки

```text
main                — стабильная защищённая ветка, только через PR владельца
rogalik-dev         — прежняя ветка прототипа и инструментов (историческая, не удаляется)
stage1-playable-combat — рабочая ветка Этапа 1 (закрыта приёмкой D15, сохраняется)
stage2-location-prototype — рабочая ветка Этапа 2 (принята приёмкой D17, сохраняется; работа в ней закончена)
stage3-hero — рабочая ветка Этапа 3 (создаётся при начале этапа от stage2-location-prototype)
agent/<задача>      — мелкие отдельные задачи, если решено вынести их из рабочей ветки
```

- Рабочая ветка этапа одна и не пересоздаётся: продолжение работы — новые коммиты в неё.
- Перед задачей: `git status`, `git branch -vv`, `git log --oneline -5`, `git ls-remote --heads origin`.
- Смена ветки только при чистом рабочем дереве.

## 4. Постоянный цикл после первой публикации

```text
задача
  → разработка (минимальный законченный кусок)
  → проверка (целевая + короткий smoke-test)
  → обновление памяти: STAGE_NN.md, PROJECT_STATE.md, при необходимости DECISIONS.md
  → локальный коммит
  → проверка синхронности памяти (tools/git/check-memory-sync.ps1 -Staged)
  → push в рабочую ветку этапа (D14, без предварительного согласования)
  → проверка факта в origin (git rev-parse origin/<ветка>) и отчёт владельцу: ветка, SHA, что проверено
```

Следующий этап начинается **в новом чате** (D12). `main` обновляется только через согласованный владельцем Pull Request.

## 5. Публикация и отчёт (D14)

Публикация выполняется автоматически после проверок; отчёт [`reports/d13_publication_report.md`](../reports/d13_publication_report.md) — обязательный, но **информационный** артефакт. Он готовится до push и уточняется после. Отчёт содержит:

1. ветку и точный SHA публикуемого коммита;
2. перечень файлов по каталогам (`docs/`, `game/`, `assets/`, `plugins/`, `tools/`, `reports/`) с количеством;
3. объём бинарников: сколько MB занимают PNG, `.pxo`, ZIP, и общий объём коммита;
4. способ загрузки ZIP и обоснование «Git LFS / без LFS» (§7);
5. что исключено и почему (кэши, производственные сборки, сторонние клоны, диагностические файлы);
6. подтверждённую целостность файлов (SHA-256 PNG по манифесту, хеш ZIP);
7. результат авторизации и фактическое состояние удалённой ветки после push.

Порядок:

```powershell
git status --short                                   # должно быть пусто
powershell -NoProfile -ExecutionPolicy Bypass -File tools/git/check-memory-sync.ps1 -Staged
git push -u origin stage2-location-prototype       # текущая рабочая ветка; первый push задаёт upstream
git rev-parse HEAD origin/stage2-location-prototype # SHA должны совпасть
git ls-tree -r origin/stage2-location-prototype -- game/prototype/scenes/ reports/
```

Только после успешной проверки в origin наличие файлов переводится в `PUSHED` (D3), а SHA фиксируется в `PROJECT_STATE.md`. Неудачный push не даёт права на `force`: сначала выясняется причина (авторизация, защита ветки, размер файла). Если причина — отсутствие авторизации, используется Git Credential Manager (§1, §8); отдельного разрешения на публикацию не требуется (D14).

## 6. Память и синхронность документов

| Файл | Когда обновляется |
|---|---|
| `docs/progress/STAGE_NN.md` | после каждой законченной задачи этапа |
| `docs/progress/PROJECT_STATE.md` | после существенного изменения (этап, коммит, блокер, следующая задача) |
| `docs/DECISIONS.md` | при новом решении владельца — в том же коммите, что и связанное изменение правил |

Проверка перед коммитом и push:

```powershell
# рабочее дерево + индекс
powershell -NoProfile -ExecutionPolicy Bypass -File tools/git/check-memory-sync.ps1
# только индекс (то, что войдёт в коммит)
powershell -NoProfile -ExecutionPolicy Bypass -File tools/git/check-memory-sync.ps1 -Staged
# конкретный коммит
powershell -NoProfile -ExecutionPolicy Bypass -File tools/git/check-memory-sync.ps1 -Commit HEAD
```

`-ExecutionPolicy Bypass` нужен потому, что в этой среде `pwsh` отсутствует, а Windows PowerShell блокирует неподписанные `.ps1` при запуске из процесса инструмента. Скрипт ничего не меняет: только читает пути и размеры и возвращает код 1 при `FAIL`.

Скрипт не заменяет решение агента, а ловит типовой промах: изменения в `game/`, `assets/`, `plugins/`, `tools/` или `reports/` без обновления `docs/progress/`, либо правка канона без записи в `DECISIONS.md`. Ненулевой код возврата — сигнал дополнить память, а не игнорировать предупреждение.

## 7. Бинарные файлы, ZIP и Git LFS

Факты на 2026-10-25:

- ZIP владельца `assets/archives/rogalik_all_concept_art_with_weapons.zip` — **65,38 MB** (68 555 000+ байт), уже в истории коммитом `61d1bda`, blob `9b4977a3…`; рабочий файл совпадает с коммитом побайтно. **ZIP не удалять и не перезаписывать.**
- 23 оригинальных PNG сверены с `docs/REFERENCE_FILE_MANIFEST.sha256`: 23/23 совпадают; плюс `hero_reference_front_back.png` и `gameplay_look_reference.png` вне ZIP.
- Предел GitHub на файл — 100 MB, поэтому ZIP проходит обычным объектом Git; предупреждение GitHub появляется на файлах > 50 MB.
- `git-lfs 3.7.1` установлен в системе, но **не используется**: перевод уже закоммиченного 65-MB blob в LFS требует перезаписи истории, что запрещено (D13). LFS-фильтры в `.gitattributes` не включаются.
- Если владелец решит уменьшить вес репозитория, допустимые варианты без перезаписи истории: (а) оставить как есть; (б) приложить ZIP как asset GitHub Release и убрать его из индекса **новым** коммитом, сохранив файл локально. Решение принимает владелец, агент не удаляет ZIP.

Правила:
- новые PNG, `.pxo`, атласы и тайлсеты включаются в Git как исходники и игровые заготовки;
- временные кэши, `.godot/`, `__pycache__`, `.cache/`, `build/`, `reports/*.log`, `*.import*.tmp`, `.env*` — исключены (`.gitignore`);
- сторонний клон `tools/godot-mcp/` (≈80,9 MB, `node_modules`) не публикуется и восстанавливается скриптом `tools/setup-godot-mcp.ps1`;
- `.gitattributes` фиксирует бинарные типы (PNG, PXO, ZIP) и не вызывает перекодировку уже закоммиченных файлов.

## 9. Безопасность

- Не читать и не выводить `.env`, токены, SSH-ключи, содержимое credential store; в отчётах только факт «авторизация подтверждена/не подтверждена».
- Не публиковать чужие репозитории, историю AI Freelancer, платные/сторонние ассеты без подтверждённых прав.
- Godot MCP bridge слушает только `127.0.0.1:9090`.
- Любая публикация сопровождается отчётом; «тихих» push не бывает.
