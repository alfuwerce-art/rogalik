# GitHub — доступ DeepSeek и правила разработки Rogalik

> Статус 2026-10-25: инструкция + утверждённый режим работы. Настройка правил GitHub в Settings выполняется владельцем. Правила в этом файле **не заменяют техническую branch protection на сервере**.

## 1. Текущее подтверждённое состояние

- Репозиторий: `https://github.com/alfuwerce-art/rogalik` (на момент проверки — публичный).
- Ветки: `main` (документы, канон) и `rogalik-dev` (Godot-прототип, плагины, скрипты, отчёты).
- Ранее агент смог отправить коммиты в `rogalik-dev`; это подтверждает, что ранее у конкретного локального сеанса существовал доступ на запись. **Не доказывает, что он всё ещё действует после перемещения Workspace.**
- На момент проверки GitHub у `main` отсутствовала branch protection (`protected: false`). Её необходимо включить перед выдачей автономных прав на `push`.

## 2. Рекомендуемая модель доступа

- Сначала использовать **существующую локальную авторизацию Git**, не создавать новый PAT/SSH-ключ без причины.
- Проверить локально в `C:\Users\bow\Desktop\Rogalik`: `git status -sb`, `git branch -vv`, `git ls-remote origin refs/heads/main refs/heads/rogalik-dev`. Не выводить адрес с паролем, токены или детали credential store.
- Владелец решает, давать ли DeepSeek право `push` в ветки `agent/*`/`rogalik-dev`. Если разрешено, агент создаёт Pull Request, но **не** сливает в `main`.
- Если существующая авторизация не работает: предпочтителен отдельный fine-grained GitHub PAT, доступ только к одному репозиторию `alfuwerce-art/rogalik`, разрешение **Contents: Read and write**; дополнительные права **Pull requests: Read and write** только если создание PR через API нужно агенту. Срок действия ограничить; не вводить токен в чат и не хранить его в файлах проекта. Авторизацию выполнить локальным безопасным способом через системный Git Credential Manager.
- Для ещё более жёсткой изоляции возможен отдельный bot account или GitHub App, но **не создавать аккаунт/приложение без отдельного решения владельца**.

## 3. Обязательная защита `main`

В GitHub: **Repository → Settings → Branches → Add branch protection rule** (либо Repository rules / Rulesets, если интерфейс показывает этот путь).

- Branch name pattern: `main`.
- Включить `Require a pull request before merging`.
- Включить `Do not allow bypassing the above settings`, если доступно, чтобы запрет соблюдался и владельцем/администраторами.
- **Не включать обязательное число одобрений (Approvals) без второго уполномоченного ревьюера:** в одиночном личном репозитории автор PR не может утвердить собственный PR как независимый ревьюер.
- `Require status checks` включить **после** настройки и фактического запуска CI; иначе можно заблокировать слияние несуществующей проверкой.
- Не разрешать force pushes и deletions. Требовать разрешения обсуждений по желанию.

После изменения проверить через GitHub UI, что `main` отображается как protected, а тестовый PR требует прохождения обычного процесса. Не пытаться проводить тест прямым push в `main`.

## 4. Цикл агента

```text
main (утверждённый стабильный код и документы)
  ↘ agent/<задача> / rogalik-dev
    → рабочие изменения → локальные тесты → коммит
    → (после разрешения) push в свою ветку → Pull Request
    → владелец проверяет кадры / код / статус → merge
```

- Не добавлять в Git историю закрытого проекта AI Freelancer.
- Сначала принять актуальные инструкции из `main` в существующую ветку (merge/rebase аккуратно, **без force** и только после сохранения незакоммиченных изменений).
- Одна содержательная задача — тематический коммит/PR; при крупном этапе допустимы последовательные проверяемые коммиты.
- После слияния проверить, что `main` собирается; не считать зелёную локальную проверку гарантией художественного качества.

## 5. Референсы и бинарные файлы

- ZIP владельца пока не получен агентом как подтверждённый источник. Не считать PNG из архивного индекса уже загруженными.
- Не заливать весь ZIP в корень репозитория; распаковать **в безопасную временную папку** и сверить с `docs/CONCEPT_ART_INDEX.md`, `docs/BOSS_REFERENCES.md`, `docs/WEAPON_REFERENCES.md`.
- Утверждённые PNG положить в `assets/references/...`, фиксируя SHA-256, размеры, имя оригинала, статус дизайна и источник.
- Игровые спрайты и тайлсеты хранить отдельно в `game/prototype/art/` или структуре, выбранной движком. **Концепт-арт не является спрайтом.**
- Проверять размеры бинарников, права на использование и необходимость Git LFS до коммита. Не совершать массовую заливку без показа списка файлов/общего объёма владельцу.
