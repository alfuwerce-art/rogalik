# AGENTS.md — правила работы ИИ-разработчиков Rogalik

> Действует для всего репозитория. Версия 2026-10-25. Перед изменениями прочитать соответствующие документы из `docs/`. Этот файл не заменяет утверждённый геймдизайн.

## 1. Проект и источники истины

- Игра: **2D top-down Action Roguelite на Godot 4.7.2 (GDScript)**. Pixel Art средней детализации, камера сверху под небольшим углом, сеттинг **«древнерусская кошмарная готика»**.
- **Единый порядок этапов:** [`docs/DEVELOPMENT_PLAN.md`](docs/DEVELOPMENT_PLAN.md) — утверждён (D6). Никакая другая система стадий не является порядком этапов проекта.
- **Решения владельца:** [`docs/DECISIONS.md`](docs/DECISIONS.md) — журнал. Решение из журнала старше любого документа и любого раздела этого файла.
- **Память между чатами:** [`docs/progress/PROJECT_STATE.md`](docs/progress/PROJECT_STATE.md) и заметка текущего этапа `docs/progress/STAGE_NN.md` — читаются в начале каждой сессии (D12, §8).
- Основной художественный канон: `docs/PIXEL_ART_STYLE_GUIDE.md`, `docs/ART_DIRECTION.md`.
- Утверждённые враги/боссы/образы: `docs/BESTIARY.md`, `docs/BOSS_REFERENCES.md`, `docs/CONCEPT_ART_INDEX.md`. Не объявлять кандидатов утверждёнными.
- Оружие, две ячейки экипировки, развитие и пять мистических сил: `docs/WEAPON_REFERENCES.md`, `docs/SKILLS_AND_BOONS.md` и другие актуальные записи канона.
- Принципы автономной работы: `docs/DEEPSEEK_GAME_DEV_RULES.md`, `docs/AI_STUDIO_PLAYBOOK.md`.
- Технический стек, команды, особенности Windows: `docs/ROGALIK_DEV_ENVIRONMENT.md`, если файл существует в текущей ветке.
- Производственный цикл: `docs/PIXEL_ART_STYLE_GUIDE.md` и общая дисциплина пакетных проходов. Устаревшие разделы с `3D mesh / rig / retarget / UV / FBX` **не применять как требования к 2D**.
- При противоречии: последнее явно утверждённое решение владельца → актуальный визуальный и игровой канон → исторические документы → гипотезы агента. Изменения самого канона требуют явного решения владельца.

## 2. GitHub и ответственность за ветки

- **`main` — стабильная, подлежащая защите ветка.** Никогда не выполнять прямой `push`, `force-push`, удаление ветки, перезапись истории или автоматическое слияние в `main`.
- **Работа в отдельных ветках**: `agent/<короткая-задача>` / `feature/<короткая-задача>` либо существующая `rogalik-dev` по согласованному этапу. Перед новой задачей проверять `git status`, активную ветку и удалённый origin.
- Агент вправе читать репозиторий, править рабочую копию, запускать безопасные локальные тесты, создавать **локальные** коммиты. `push` рабочих веток / создание Pull Request допускаются после подтверждения владельцем подключения GitHub и выданных полномочий на соответствующий этап. Никаких скрытых публикаций.
- **Текущее ограничение (D5, 2026-10-25): `push`, Pull Request и merge в GitHub запрещены.** Разрешены только локальные коммиты. Это ограничение отменяет разрешающую часть предыдущего пункта до отдельного решения владельца.
- PR должен описывать: цель, изменённые файлы, фактически выполненные проверки, игровые кадры/сцены по необходимости, известные дефекты. В `main` сливает владелец после просмотра; агент не нажимает Merge.
- Не выполнять `git reset --hard`, `git clean -fdx`, удаление файлов, массовое переименование или `force` без ясного разрешения на конкретные затрагиваемые данные. Не вычищать данные «на всякий случай».
- Не добавлять чужие репозитории, историю AI Freelancer, кэши, виртуальные окружения, build-артефакты и временные журналы.

## 3. Практический цикл задачи

1. Проверить текущее состояние Git и прочитать **только релевантный** канон. Сформулировать цель, границы изменений и конкретный проверяемый результат.
2. Внести минимальные работоспособные изменения в код, сцену или спрайт. Использовать существующие Godot/Pixelorama/PowerShell/MCP-инструменты прежде, чем писать новые плагины.
3. Проверить затронутое поведение: импорт ассетов, синтаксис GDScript, запуск сцены, коллизии/попадания, ошибки; выполнить один короткий интеграционный smoke-test. Не повторять весь тяжёлый набор после каждой мелкой правки.
4. При новых визуальных ассетах проверить **реальный игровой масштаб**: силуэт, анимацию, читаемость атаки, отсутствие размытия/дребезжания пикселей.
5. Исправить наблюдаемые дефекты; после двух существенно разных безрезультатных попыток зафиксировать точный `BLOCKER` и требуемую помощь.
6. Сделать небольшой тематический коммит и отчёт: `DONE / TESTED / NOT_VERIFIED / BLOCKED`, путь к результату, SHA коммита, следующие действия. Не выдавать написанный план за работающую игру.
7. **Одна задача — одна целевая проверка. Один этап — одна итоговая приёмка.** После изменения проверяется только затронутый риск и один короткий smoke-test. Полный набор — при закрытии этапа ([`docs/DEVELOPMENT_PLAN.md`](docs/DEVELOPMENT_PLAN.md) §2). Доказательства переиспользуются, а не переснимаются.

**Приоритет — играбельный вертикальный срез**, затем масштабирование по пакетным стадиям на согласованный состав. Нельзя полировать одного босса до финала, пока отсутствует рабочее движение/боёвка. Технические `PROXY_TECHNICAL` разрешены; художественная приёмка по референсам отдельно.

## 4. Границы самостоятельности

**Можно без постоянного согласования:** писать код/сцены в рабочей ветке, создавать `PROXY_TECHNICAL`, проверять спрайты, запускать Godot и Pixelorama, проводить тесты, чинить локальные ошибки, вести локальные коммиты и техотчёты.

**Только после явного разрешения:** изменять утверждённую художественную/игровую концепцию, полностью заменять движок, платно пользоваться API или скачивать платные ассеты, устанавливать исполняемые сторонние компоненты или изменять профиль Harness, удалять значимые данные, давать права GitHub/секреты, выполнять публикации за рамками разрешённой ветки/этапа.

Нельзя молча загружать локальные пользовательские файлы, изображения, журналы или секреты во внешние сервисы.

## 5. Работа с референсами

- Оригиналы из ZIP — **визуальные источники**, не готовые игровые PNG-спрайты. Игровые экспорты хранить отдельно от оригиналов.
- Путь по типу: `assets/references/bosses/`, `assets/references/enemies/`, `assets/references/weapons/`, `assets/references/locations/`, `assets/references/hero/`; сверяться с `docs/CONCEPT_ART_INDEX.md` и `docs/REPOSITORY_STRUCTURE.md`.
- До распаковки: перечислить состав ZIP, размеры, дубликаты, небезопасные имена/пути и возможные лицензии. Не исполнять содержимое архива.
- Не перезаписывать утверждённый оригинал другим изображением; сравнивать SHA-256 с известными записями, сохранять исходное разрешение и имя в манифесте.
- Статусы присваивать по трём осям из §7 — художественное решение, наличие файла, готовность ассета. Одно значение не заменяет другое. Никогда не объявлять отсутствующий или неутверждённый референс утверждённым.
- Импортировать в Git только нужные исходники/экспорты, без повторного коммита всего ZIP; при необходимости больших файлов сначала согласовать Git LFS. Не удалять ZIP владельца.

## 6. Безопасность и качество

- Не читать и не печатать `.env`, токены GitHub, приватные SSH-ключи, конфиги с паролями. Не писать секреты в репозиторий или отчёты.
- Любые внешние MCP/плагины: проверять источник, лицензию, зависимости, локальные права и фактический вызов. Godot runtime bridge должен слушать только `127.0.0.1`.
- Вся добавленная графика и код должны иметь понятное происхождение и разрешённое использование.
- Простой `headless` тест не доказывает визуальное качество. Важны реальные кадры и работающее управление.
- Не выдавать 10 предупреждений за ошибку сборки или «всё идеально»: указывать, что проверено, а что не проверено.

## 7. Статусы — единый словарь (D3)

Статус художественного решения, наличие файла и готовность игрового ассета — **три независимые оси**. Нельзя выводить одну из другой: утверждённый концепт не означает наличия PNG, наличие PNG не означает готового ассета.

**Ось 1 — художественное решение:**

| Значение | Смысл |
|---|---|
| `VISUAL_APPROVED` | Референс внешности утверждён владельцем; по нему можно разрабатывать |
| `VISUAL_CANDIDATE` | Предложен, не утверждён; финальный арт запрещён |
| `LOOK_REFERENCE` | Ориентир настроения/вида, не утверждённая единица |
| `NO_REFERENCE` | Референса нет → `BLOCKED_NEEDS_REFERENCE`, внешность не придумывать |

**Ось 2 — наличие файла:**

| Значение | Смысл |
|---|---|
| `ABSENT` | Файла нет ни локально, ни в репозитории |
| `LOCAL_ONLY` | Есть только в рабочей копии, не закоммичен |
| `COMMITTED_LOCAL` | Есть в локальном коммите; в GitHub может отсутствовать |
| `PUSHED` | Подтверждён в удалённой ветке GitHub |

**Ось 3 — готовность игрового ассета:**

| Значение | Смысл |
|---|---|
| `NONE` | Игрового ассета нет |
| `PROXY_TECHNICAL` | Временная техническая заготовка; в финальную сборку как арт не идёт |
| `ASSET_DRAFT` | Рабочий ассет, не прошедший художественную приёмку |
| `ASSET_APPROVED` | Принят владельцем как финальный |

**Статусы работ и этапов:** `TODO` · `IN_PROGRESS` · `PASS` · `FIX_REQUIRED` · `NEEDS_REVIEW` · `BLOCKED` · `BLOCKED_NEEDS_REFERENCE` · `NOT_VERIFIED`. «Готово» без проверки не существует.

**Устаревшие имена (не использовать):** `APPROVED_CONCEPT`, `CANDIDATE_CONCEPT`, `PNG_PRESENT`, `PNG_MISSING`, `PNG_IN_REPO`, `GAME_ASSET_READY`, `NOT_READY`, `PROXY` без уточнения.

**Где смотреть фактические значения:** [CONCEPT_ART_INDEX.md](docs/CONCEPT_ART_INDEX.md) — герой, оружие, локации, артефакты; [BESTIARY.md §0](docs/BESTIARY.md) — боссы и враги; [DEVELOPMENT_PLAN.md §5](docs/DEVELOPMENT_PLAN.md) — состояние этапов.

## 8. Межчатовая память и границы этапа (D12)

**Каждый новый этап разработки начинается в отдельном новом чате DeepSeek Harness с пресетом `Rogalik Dev`.** Контекст передаётся файлами в репозитории, а не памятью модели и не историей чатов.

### Начало нового чата — обязательный порядок

1. Проверить фактическую рабочую директорию, ветку и `git status`; убедиться, что активна ожидаемая ветка.
2. Прочитать `AGENTS.md` → `docs/DEVELOPMENT_PLAN.md` → `docs/DECISIONS.md`.
3. Прочитать [`docs/progress/PROJECT_STATE.md`](docs/progress/PROJECT_STATE.md).
4. Прочитать заметку текущего этапа `docs/progress/STAGE_NN.md`.
5. При необходимости — заметки предыдущего этапа.
6. **Сверить заметки с фактическими файлами и Git.** Расхождение фиксируется как `DISCREPANCY` с причиной; факты не подгоняются под память, и работа не начинается до выяснения.
7. Продолжить с последней незавершённой задачи этапа. **Не начинать следующий этап без приёмки текущего владельцем.**

### После каждой законченной задачи

- обновить `docs/progress/STAGE_NN.md`;
- обновить `PROJECT_STATE.md`, если изменилось состояние (этап, коммит, блокер, следующая задача);
- сделать локальный коммит.

### Перед закрытием этапа

- проверить полноту заметки: все 11 обязательных разделов заполнены;
- указать точные результаты, файлы и локальные коммиты;
- записать известные ограничения и то, что осталось непроверенным;
- подготовить короткую (5–10 строк) передачу контекста для следующего чата;
- **остановиться до приёмки владельцем.** Статус `ACCEPTED` ставит только владелец.

### Замена чата до окончания этапа

Новый чат называется **«Этап N — продолжение»** и загружает ту же память (`PROJECT_STATE.md` + `STAGE_NN.md`). Начинать этап заново запрещено.

### Файлы памяти

| Файл | Назначение | Когда создаётся/обновляется |
|---|---|---|
| `docs/progress/PROJECT_STATE.md` | краткое состояние «сейчас» | после существенного изменения |
| `docs/progress/STAGE_NN.md` | история одного этапа (11 разделов) | создаётся при начале этапа, обновляется после каждой задачи |

Пустые журналы будущих этапов заранее не создаются. Память **не заменяет Git**: источник истины о фактах — `git log`, реальные файлы и выполненные запуски.
